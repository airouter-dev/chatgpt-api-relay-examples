Build the same production-minded image workflow in **Python, Node.js, C++, Go, Rust, and PHP**:

1. Generate an image from a text prompt with the OpenAI-compatible `/images/generations` endpoint.
2. Save the returned image locally.
3. Send that file to `/images/edits` with a transformation prompt.
4. Save the edited result and print both artifact paths.

The project is a practical starting point for developers who want to evaluate image models from several ecosystems without rewriting their application around a vendor-specific SDK. It uses AI-ROUTER, an independent OpenAI-compatible API service. The API endpoint is configurable, so the same code can be pointed at a compatible gateway in a private environment.

> AI-ROUTER is not an OpenAI product. Model availability, quotas, prices, image sizes, and optional fields depend on the authenticated account and current service configuration. Check the service documentation and your account's model list before running a request.

## What this repository demonstrates

### A realistic two-stage product flow

The examples intentionally persist the generated artifact before editing it. That mirrors a reviewable product workflow: a user can inspect the first draft, keep it as a variant, and then submit a controlled edit. The edit call uses multipart upload and does not rely on an undocumented provider-specific shortcut.

### Consistent architecture across languages

Every implementation separates configuration, transport, workflow, and CLI concerns. The HTTP client is reusable from a web server or background worker; the workflow is reusable from a job queue; the CLI is only an adapter. See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) and the shared [API contract](docs/API_CONTRACT.md).

### Configurable model and size

Set `AI_ROUTER_MODEL` to a model enabled for your account. The examples support model names such as `gpt-image-2`, `gpt-image-2.5`, `gpt-image-2.5-flare`, and `gpt-image-2.5-burst` without assuming that every account exposes every model. Pass a different `--model` or `--size` when experimenting. Python and Node.js retain `IMAGE_*`/`OPENAI_*` aliases where useful for compatibility with existing clients.

### Safe defaults for a public example

No credentials are committed. Output directories are ignored. Errors include status and bounded diagnostics without leaking the bearer token. The examples use HTTPS and make the base URL explicit so users can audit where data is sent.

## A closer look at the two-step workflow

The generation and edit operations are deliberately visible as separate HTTP requests:

```text
prompt ──POST /images/generations──> generated bytes ──save──> draft.png
draft.png + edit instruction ──POST /images/edits──> edited bytes ──save──> result.png
```

The first image is not discarded or kept only in memory. Persisting it creates a useful review point and makes a failed edit recoverable without paying to repeat generation. It is also the exact file uploaded as the multipart `image` field, so readers can inspect how real image-to-image editing differs from sending another prompt to the generation endpoint.

### When to call each endpoint

| Need | Operation | What goes over the wire |
| --- | --- | --- |
| Create a new visual from a description | `POST /images/generations` | JSON containing a model ID, prompt, size, and response preference |
| Change an existing or generated visual | `POST /images/edits` | Multipart fields plus the source image file and an edit instruction |
| Keep a human approval step | Save between operations | A local draft that can be reviewed, versioned, or replaced by object storage |

This structure fits product mockups, editorial illustrations, campaign concepts, asset pipelines, creative tooling, and prototyping. It does not define a public upload service, guarantee that a model will preserve every detail, or replace human review for production assets.

## Prompt design for useful iterations

Prompt quality is easier to evaluate when the instruction states a subject, composition, visual treatment, and one or two constraints. Keep the first generation prompt focused; put a controlled, narrow change in the edit prompt. If every part of an image changes at once, it becomes harder to compare model behavior across languages or tell whether the edit operation used the input image as intended.

| Stage | Example instruction | Why it is useful |
| --- | --- | --- |
| Generation | `A compact glass greenhouse on a rainy rooftop, editorial photography, wide composition, cool morning light` | Establishes subject, setting, framing, and treatment |
| Edit | `Keep the greenhouse and framing unchanged; shift the lighting to warm golden hour` | Requests a specific change and names the elements to preserve |
| Product variation | `A matte black reusable bottle on a pale stone plinth, soft studio light, no text` | Gives a repeatable baseline for design exploration |
| Illustration variation | `Turn the scene into a hand-painted gouache illustration with visible brush texture` | Changes a visual treatment while leaving room to compare the source |

More prompt ideas are in [`examples/prompts.md`](examples/prompts.md). For an experiment, use the same prompt, edit prompt, model, and size in each language implementation; the different code paths should not quietly change the test scenario.

## Choosing a model and size

The examples accept a model ID at runtime rather than maintaining a supposedly universal catalog. Names such as `gpt-image-2`, `gpt-image-2.5`, `gpt-image-2.5-flare`, and `gpt-image-2.5-burst` are examples to try only when they are visible and enabled for your account. A model name in a README is not a claim of availability, provider affiliation, price, quality level, or ongoing support.

Start with the size and quality options shown for the selected account/model. The default `1024x1024` is a demo default, not a guarantee that every compatible upstream supports it. Keep the requested size, actual output dimensions, and a provider's internal generation process conceptually separate: a response field is protocol metadata, not proof of how an image was produced.

## Quick start

### 1. Create an AI-ROUTER key

Open the [AI-ROUTER dashboard](https://ai-router.dev), create an API key with access to an image model, and verify the model is visible to your account. Do not use a provider secret here; the demo only needs the AI-ROUTER key.

```bash
cp .env.example .env
# edit .env and set AI_ROUTER_API_KEY
```

All CLIs also read the process environment directly. The `.env` file is documentation-friendly but is not loaded automatically by every runtime; export the variables in your shell or use your preferred dotenv loader.

### 2. Run one language

Each language has a focused README with installation and exact commands. The common conceptual command is:

```text
demo --prompt "A tiny glass greenhouse on a rainy rooftop" \
     --edit-prompt "Change the lighting to warm golden hour" \
     --model gpt-image-2
```

The command creates an ignored output directory containing a generated draft and an edited result; filenames are documented by each language (for example, `generated.png`/`edited.png` or `rust-generated.png`/`rust-edited.png`).

### 3. Compare implementations

Use the same prompt, model, size, and API key in each directory. Compare startup cost, binary/container size, error ergonomics, and how naturally each client can be embedded into your application. This repository is designed to make that comparison fair: the HTTP fields and two-step workflow are intentionally identical.

## Text-to-image and image-to-image contract

The generation request is JSON:

```json
{
  "model": "gpt-image-2",
  "prompt": "A tiny glass greenhouse on a rainy rooftop",
  "size": "1024x1024",
  "n": 1,
  "response_format": "b64_json"
}
```

The edit request is multipart with `model`, `prompt`, `size`, `response_format`, and the generated file under the `image` field. The clients accept `b64_json` responses and fail clearly when a response contains neither a base64 image nor a supported URL. Read [`docs/API_CONTRACT.md`](docs/API_CONTRACT.md) for the exact behavior and extension points.

## Production hardening checklist

Before turning a demo into a customer-facing endpoint:

- validate prompt length, image MIME type, dimensions, and upload size;
- add bounded retries with jitter only for safe, retryable failures;
- use a durable object store and lifecycle policy instead of local disk;
- redact prompts and response metadata from logs where they can contain personal data;
- add request authentication, per-user quotas, abuse controls, and content policy checks;
- record request IDs and usage data for support without logging API keys;
- configure timeouts, cancellation, circuit breaking, and metrics for your runtime;
- confirm model, size, pricing, and data-retention behavior with your AI-ROUTER account.

The security guidance is collected in [`docs/SECURITY.md`](docs/SECURITY.md). These samples are intentionally transparent rather than pretending to be a complete public upload service.

## Troubleshooting

**401 or 403:** confirm `AI_ROUTER_API_KEY` is exported, has not expired, and is allowed to use the selected model.

**Model unavailable:** call `GET https://api.ai-router.dev/v1/models` with the same bearer token and choose a model returned for your account.

**Unsupported size:** use the size values accepted by the account/model. Start with `1024x1024`.

**No image in the response:** check the raw request ID and the bounded error printed by the client. Some compatible deployments may return a URL rather than `b64_json`; the examples document the portable base64 path and report unsupported response shapes rather than silently writing an empty file.

**Edit fails after generation:** keep the generated file. The workflow deliberately treats it as a valid artifact and reports the edit failure separately, which is useful for retries or manual review.

## Local validation

The Node.js suite passes with `npm test`; the Go implementation passes `go test ./...`, `go vet ./...`, and `go build ./cmd/imagegen`. The C++ project is wired for CMake/CTest, but this Windows workspace does not have a C++ compiler/libcurl development toolchain configured. Python, Rust, and PHP source and configuration were reviewed statically here because their runtimes are not installed. Run their language-specific commands in CI before publishing a release tag.

## Responsible use

Only upload images and prompts you are permitted to process. Do not place API keys, private customer data, or secrets in prompts. Follow the applicable provider terms, local law, and your AI-ROUTER account policy. Generated content may require human review before publication.
